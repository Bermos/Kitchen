# Security review — Kitchen at main `2eac151` (2026-09-03)

Scope asked for: the platform itself, the projects it deploys, and the compliance
suite, after issue #270 and its eight sub-issues landed (#288, #290, #291, #292,
#295, #296, #297 on `main`; PR #293 was closed unmerged).

**Coverage is partial.** The review was run as eight parallel code-reading
passes; usage limits killed five of them before they wrote anything. What is
below is the output of the three that finished (identity provider, claims and
connections, dashboard and CLI) plus dependency and chart-lint scans. The five
areas with **no findings recorded** are listed at the end — absence there is not
a clean bill.

Severity is judged inside the stated threat model (docs/AUTH.md: "cluster
access is operator access"; docs/SCOPE.md: no multi-tenant SaaS model), and
says so when a finding only matters outside it. Every finding cites the code
that was read; none was reproduced at runtime.

---

## High

### 1. Any OAuth client the issuer knows can mint tokens the API accepts, for any user who consents
- **Impact.** A project `developer` creates an `oidcClient` claim (or a CI-key
  holder registers a client directly, see #5). Their app shows "Sign in with
  Kitchen"; the consent page lists scopes, never the audience. The app then
  exchanges the code with `resource=https://kitchen.<baseDomain>` and gets a JWT
  with the API as audience. The API accepts it as that user with every role the
  user holds. An operator who signs into a colleague's app hands it operator
  API access for an hour, renewable for a week with `offline_access`.
- **Where.** `auth/src/auth.ts:97` (`validAudiences` is issuer-wide, not
  per-client); `@better-auth/oauth-provider` `checkResource` only checks
  membership in that list; `internal/api/auth.go:236-257,301-318`
  (`SkipClientIDCheck: true`, `azp` carried but never checked);
  `internal/controller/resourceclaim_oidc.go:165-170,402-412` (developer-chosen
  redirect URIs go verbatim into registration, any `https://` host passes).
- **Fix.** In `authenticate`, refuse tokens whose `azp` is present and is not
  one of the platform's own clients (dashboard, CLI); keep accepting
  session-minted tokens with empty `azp` (the CI-key path). In `auth.ts`, add a
  `before` hook on `/oauth2/token` that strips or refuses `resource` for any
  client other than the dashboard client. If third-party API access is ever a
  feature, show the requested resource on the consent page.

### 2. A retained claim resource is re-bound by name alone, across projects
- **Impact.** Provider-side objects are named `kitchen-<claim>` with no project
  component and no project label. After a claim is deleted with the default
  `Retain` policy (or its project is deleted), any developer of any other
  project creates a claim with the same name against the same Connection and
  is bound to the old project's CloudNativePG database, MinIO bucket (the
  scoped credential is re-issued to the new claimant) or Valkey instance,
  production data included. Neon adopts any project named `kitchen-<name>` in
  the account.
- **Where.** `internal/controller/resourceclaim_postgres.go:625-627`,
  `resourceclaim_redis.go:223`, `internal/provider/database/cnpg.go:264-274,368`,
  `database/neon.go:72-89`, `provider/cache/valkey.go:371-381,455-461`,
  `provider/objectstore/s3.go:186-230`, `objectstore/names.go:46`;
  `internal/api/policy.go:618-619` (`POST /claims` needs only
  `ProjectDeveloper`). docs/api/claims.md:74-77,150-152,449-454 document the
  rebind without a project qualifier.
- **Fix.** Name provider objects `kitchen-<project>-<claim>` (with the existing
  hash truncation) and label or tag them with `kitchen.bermos.dev/project`;
  refuse to adopt an object whose project differs and surface that on the
  claim's condition. Same for Neon project names and MinIO bucket tags.

### 3. An external `redis` Connection gives every project the same database and password
- **Impact.** All production claims through one `redis` Connection bind to
  `<url>/0` with the Connection's own password, so project A's app can read,
  overwrite and `FLUSHALL` project B's cache or queue. Previews get
  `1 + hash(env) mod (n-1)` with no collision handling, and `DeleteBranch` is a
  no-op, so a new preview inherits a previous preview's keys. docs say "a claim
  gets one and every preview of it gets another", which the code does not do.
- **Where.** `internal/provider/cache/external.go:95-106,115-127,133-137,166-208`.
- **Fix.** Allocate a database number per claim and persist the allocation on
  the Connection status, or better, create a Redis ACL user per claim
  (`ACL SETUSER <user> on ><pw> ~<prefix>:* -@dangerous +@all`) and hand that
  user out in the binding. Until then, document the Connection as single-project.

### 4. The CLI's repository link file can redirect CI credentials to an attacker's host
- **Severity note.** High outside the model (malicious commit or fork PR);
  Medium inside it (any committer can steal the project's CI key).
- **Impact.** With `KITCHEN_API_KEY` or `KITCHEN_TOKEN` exported and no
  `--api`/`KITCHEN_API` set (the pattern docs/CLI.md recommends), the CLI takes
  the API base from `.kitchen/project.json`, found by walking up from the
  working directory. It fetches `<base>/config.json`, trusts the `issuer` in
  it, and posts the raw key as `x-api-key` to `<issuer>/token`, or sends the
  bearer token to `<base>/api/v1/...`. A committer sets `"api":
  "https://attacker"` and collects a long-lived role-holding credential. Go
  strips `Authorization` on cross-host redirects but not `x-api-key`.
- **Where.** `internal/cli/runtime.go:130-160,196-272`,
  `internal/cli/config.go:190-225`, `internal/cli/client.go:452-461`.
- **Fix.** Let the link file choose among installations already present in
  `auth.json` or named by `KITCHEN_API`, never introduce a new base. Accept an
  issuer from `/config.json` only if it is on the API's registrable domain, or
  pin it at login. Set `CheckRedirect` to refuse redirects on the exchange.
  Tell CI users to set `KITCHEN_API` explicitly.

## Medium

### 5. A CI key is a full identity-provider session, not a one-project credential
- **Impact.** With `enableSessionForAPIKeys: true`, an `x-api-key` becomes a
  session on every better-auth endpoint. `clientPrivileges` is not set, so a CI
  key can `POST /oauth2/register` confidential clients with arbitrary `https://`
  redirects and `client_credentials` grant (feeding #1) that the operator's
  `/kitchen/clients` cannot see, and can `POST /api-key/create` further keys
  for its machine account with no expiry; `listProjectKeys` shows one row per
  account so those extra keys are invisible (revocation still catches them).
- **Where.** `auth/src/auth.ts:81-89,159-164`; `auth/src/clients.ts:106-117`;
  `auth/src/keys.ts:373,423-426`.
- **Fix.** Set `clientPrivileges` so only the service account may register or
  manage clients. Add a `before` hook that refuses `x-api-key` requests outside
  an allowlist (`/token`, `/get-session`, `/kitchen/*`), or at least refuses
  `/api-key/*` and `/oauth2/register` for machine accounts. Add tests for both.

### 6. The "private" `/kitchen/*` prefix and the service key are reachable from the internet
- **Impact.** The auth HTTPRoute sends `PathPrefix /` of `auth.<baseDomain>` to
  the service and there is no NetworkPolicy in the chart. Whoever holds
  `serviceKey` can, from anywhere: enumerate every account, mint CI keys for any
  project, delete keys, and rewrite every operator-registered OAuth client's
  redirect list (an account-takeover primitive against every app using an
  `oidcClient` claim and against the preview gate). The seeded key row has
  `rateLimitEnabled: false` and the custom prefix is outside better-auth's
  limiter. The key is 64 random alphanumerics compared by SHA-256 lookup, so
  brute force is impractical; this is exposure of a leaked key, not guessing.
- **Where.** `charts/kitchen/templates/auth/httproute.yaml:187-193`,
  `auth/src/server.ts:221-244`, `auth/src/directory.ts:151-183`,
  `auth/src/seed.ts:395`.
- **Fix.** Serve `/kitchen` on a second Service or port that the HTTPRoute does
  not reference (the operator already uses `internalURL`), or add a route rule
  matching `PathPrefix /kitchen` that answers 404. Rate-limit and log source
  address on refusals.

### 7. A `developer` can create and delete claims with `deletionPolicy: Delete`
- **Impact.** `DELETE /claims/{name}` at developer role on a `Delete`-policy
  claim removes the CNPG Cluster and PVCs, every object version in the bucket
  (`GovernanceBypass: true`), or the Valkey StatefulSet and PVC. Under the
  compliance regime's segregation-of-duties expectation this is High.
- **Where.** `internal/api/policy.go:618-622`, `internal/api/claims.go:165-171`,
  `resourceclaim_postgres.go:178-183`, `objectstore/s3.go:154-177`,
  `cache/valkey.go:646-674`.
- **Fix.** Require `ProjectAdmin` to set `Delete` on create and to delete a
  `Delete`-policy claim, with the type-the-name confirmation the project
  deletion already uses.

### 8. Dashboard tokens live in `localStorage`; no CSP or other security headers
- **Impact.** The rotating refresh token is readable by any script on the
  dashboard origin (future XSS, compromised npm dependency, extension). No CSP,
  no `frame-ancestors`/`X-Frame-Options`, so the confirm-by-typing deletion and
  membership screens can be framed. No XSS was found (no `v-html`, no
  `innerHTML`, nothing loaded from a CDN), which is why this is Medium.
- **Where.** `ui/src/lib/auth.ts:36-72,206-247`; `internal/ui/ui.go:88-141`
  (sets only `Content-Type` and `Cache-Control`); no `ResponseHeaderModifier`
  on any HTTPRoute.
- **Fix.** In `internal/ui/ui.go` set `Content-Security-Policy: default-src
  'self'; script-src 'self'; style-src 'self' 'unsafe-inline'; img-src 'self'
  data:; connect-src 'self' <issuer>; font-src 'self'; frame-ancestors 'none';
  base-uri 'none'; form-action 'self'`, plus `X-Content-Type-Options: nosniff`,
  `Referrer-Policy: no-referrer`, `X-Frame-Options: DENY`. Consider keeping the
  refresh token in memory with a `BroadcastChannel` for tabs.

### 9. Vulnerable Go dependencies with reachable symbols
- `govulncheck ./...` reports the code is affected by nine advisories in two
  modules: `github.com/cilium/cilium v1.17.6` (GO-2026-5914, -5905, -5400,
  -4856, GO-2025-4167; fixed in 1.17.14/1.17.15) and
  `github.com/prometheus/prometheus v0.303.0` (GO-2026-5710, -5662, -5381,
  -5264; fixed in 0.311.3). Most are only relevant when the vulnerable
  component runs in this binary (Prometheus web UI, remote read), so real
  exposure is likely low, but the symbols are reachable and the bump is cheap.
- **Fix.** Bump both modules in `go.mod`; re-run `govulncheck`.

### 10. No NetworkPolicy anywhere; platform data stores reachable from every app namespace in plaintext
- **Impact.** docs/SCOPE.md deprioritises inter-app policies on purpose, but
  the consequence is concrete: any application pod (including a preview built
  from a pull request) can reach `*.kitchen-databases.svc`,
  `*.kitchen-caches.svc`, `kitchen-objectstore.kitchen-system.svc:9000`, the
  OTLP collector and ClickHouse, credentials permitting. The CNPG binding URL
  has no `sslmode` (libpq `prefer`, unverified), Valkey is `TLS: false`, MinIO
  is `http://`. With #1 and #2 above this is the path from "one malicious
  preview" to "another project's data".
- **Where.** `grep -rl NetworkPolicy charts/` is empty; `database/cnpg.go:465-470`,
  `cache/valkey.go:627-639`, `controller/objectstore.go:66-68`.
- **Fix.** Add `?sslmode=require` to the CNPG DSN now. Ship a default-deny
  CiliumNetworkPolicy per app namespace allowing egress to the environment's
  own bindings, the Gateway, DNS and the collector, and ingress from the
  Gateway and the gate only. Reconsider the SCOPE decision now that the
  compliance suite claims segregation between projects.

## Low

- **11. Bootstrap endpoint.** GET answers 410 vs 401 before checking the token,
  so an unauthenticated probe learns whether the install has been bootstrapped
  yet; two concurrent valid POSTs can both create a "first administrator" (no
  lock). `auth/src/server.ts:265-272`, `bootstrap.ts:326-328,363-368`. Check
  the token first; wrap creation in the existing advisory lock.
- **12. Valkey image tags float** (`valkey/valkey:8.1-alpine`) despite the
  comment saying digest-pinned, and `--requirepass $(VALKEY_PASSWORD)` puts the
  password in argv. `provider/cache/valkey.go:89-92,559-560`. Pin digests;
  move the password into a mounted `valkey.conf`.
- **13. Inngest previews share account-wide branch keys**, so a preview of
  project A can address project B's branch environment by changing
  `INNGEST_ENV`. `provider/inngest/cloud.go:100-137`. No API fix exists;
  document it and offer a Connection per project.
- **14. Terminal escape injection in `kitchen logs` / `kitchen deploy`.**
  Server-supplied lines are printed raw; an application (or a build from a
  malicious repo) can rewrite the operator's terminal. `internal/cli/client.go:333-388`,
  `cmd_api.go:126-129`. Strip non-printable runes in the non-JSON printer.
- **15. Chart lint (kube-linter on the rendered chart).** Collector DaemonSet
  runs as root with the host's `/` mounted (by design, but `/var/log` would
  do); ClickHouse and Postgres containers without read-only root filesystem;
  restore Job without `ttlSecondsAfterFinished` or resource limits; bundled
  cert-manager without requests/limits.
- **16. `@tiptap/core` prototype-pollution advisory** (27 moderate entries from
  `npm audit --omit=dev`, all via `@nuxt/ui` 4.10.0). No editor is mounted, so
  unexploitable as shipped; bump when `@nuxt/ui` moves.

## Info

- Better-auth's `/token` puts the whole user row in the JWT and any signed-in
  browser can mint one; a dashboard XSS converts directly to an API bearer.
- Social sign-in links implicitly to an existing account with the same
  verified email (better-auth default; bootstrap admin is created verified).
  Set `accountLinking.disableImplicitLinking: true` if explicit linking is
  wanted, and say so in docs/AUTH.md.
- Neon, Inngest and S3 clients use `http.DefaultClient` with no timeout.
- `target="_blank"` links lack `rel="noopener noreferrer"` (browsers imply
  `noopener`; cosmetic).

## Checked and found sound (by the three completed passes)

- Password sign-up disabled unconditionally; bootstrap token timing-safe and
  never logged; service key stored hashed, never echoed, refused to CI keys and
  browser sessions; every `/kitchen` route behind the one `authenticate`.
- Dynamic registration refuses anonymous callers; `skip_consent` cannot be set
  at registration; redirect URIs exact-match with loopback-only relaxation;
  PKCE S256 mandatory for public clients; refresh tokens rotate and replay
  revokes the family; access 1h / refresh 7d; EdDSA JWKS with private key
  encrypted at rest; API pins the alg list and refuses `none`.
- Cookies `__Secure-`, `HttpOnly`, `SameSite=Lax`; CORS and trusted origins
  from one list, never `*`; 16 KiB body cap on the auth service; auth container
  non-root, read-only root, all caps dropped, seccomp RuntimeDefault.
- CNPG: one Cluster per claim, fresh empty Cluster per preview, non-superuser
  `app` role, no identifier interpolation from user input; extension names
  through a closed alphabet. Neon: token only in headers, `sslmode=require`,
  branches deleted on preview close. MinIO: per-bucket user with bucket-scoped
  policy, root credential never handed out when `scopedCredentials` is on.
  Valkey: 32-byte random password per instance, non-root, caps dropped.
- OIDC claim redirect list only includes this project's environments and
  verified Domains; a verified Domain of another project cannot enter it.
- Preview-mode defaults after 0.22.0 are provider-declared isolation
  (neon=branch, cnpg/s3/valkey/redis/volume=fresh, inngest=branch,
  oidcClient=shared holding no data); `shared` refused where a provider forces
  recreate.
- `POST /claims` resolves the caller's role on the project in the body;
  bindings are written only into that project's namespace; credentials never
  appear in claim views, audit details or provider errors.
- Dashboard: Authorization Code + PKCE, `state` from `crypto.getRandomValues`,
  RFC 8707 `resource=` on exchanges, bearer sent only to the API origin,
  `returnTo` resolved in-app (no open redirect), no `v-html`/`innerHTML`/CDN
  loads, UI policy table generated from the API's and rendering-only, static
  serving through `embed.FS` with `path.Clean`.
- CLI: `auth.json` written 0600 in a 0700 dir via temp-and-rename; no
  `InsecureSkipVerify` or `--insecure`; git shell-outs use fixed argv; no local
  callback listener; download filenames validated; NDJSON never drives local
  actions.
- No `InsecureSkipVerify` anywhere under `internal/` or `cmd/`.
