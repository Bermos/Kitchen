TLS mode is "acme": the operator requests a wildcard certificate for
*.{{ .Values.kitchen.baseDomain }} into the secret "kitchen-wildcard-tls". It appears a reconcile
after cert-manager starts answering, not with the rest of the release:

  kubectl get kitchen default -o jsonpath='{.status.conditions[?(@.type=="CertificateReady")].message}'
  kubectl -n {{ .Release.Namespace }} get certificate kitchen-wildcard

The order is solved over DNS-01, with the Cloudflare token in the secret
"{{ .Values.kitchen.tls.acme.dns01.cloudflare.apiTokenSecretName }}". That is not a preference: every generated URL is a
subdomain of the base domain, so the platform needs a wildcard, and ACME issues
wildcards over DNS-01 alone.
{{- else }}

TLS mode is "acme" but kitchen.tls.acme is not configured, so the platform
manages no certificate and the Gateway's HTTPS listener has nothing to
terminate with. Set kitchen.tls.acme.email and
kitchen.tls.acme.dns01.cloudflare.apiTokenSecretName, or choose another
kitchen.tls.mode.
{{- end }}
{{- end }}

release publishes — the OIDC issuer among them — is http://. Logins work, but
over plain HTTP: fine for bringing a cluster up before DNS and certificates
exist, not for running one.
{{- end }}

{{ if .Values.api.route.enabled -}}
The operator's REST API answers at:

  {{ include "kitchen.scheme" . }}://{{ include "kitchen.apiHost" . }}/api/v1/projects

Every endpoint needs a bearer token from the identity provider. Exchange an API
key for one, then call the API with it:

  TOKEN=$(curl -sS -H "x-api-key: $KITCHEN_API_KEY" {{ include "kitchen.authIssuer" . }}/token | jq -r .token)
  curl -sS -H "authorization: Bearer $TOKEN" {{ include "kitchen.scheme" . }}://{{ include "kitchen.apiHost" . }}/api/v1/projects
{{- else -}}
The REST API is only reachable in-cluster (svc/{{ include "kitchen.fullname" . }}-api). Expose it,
or set api.route.enabled=true, before pointing a UI or a CLI at it.
{{- end }}

{{- if (include "kitchen.previewGateEnabled" .) }}

Preview URLs are gated behind that login. The operator registers an OAuth client
and runs the gate at {{ include "kitchen.previewGateHost" . }} — it appears a reconcile after the
identity provider starts answering, not with the rest of the release:

  kubectl get kitchen default -o jsonpath='{.status.conditions[?(@.type=="PreviewGateReady")].message}'

Point {{ include "kitchen.previewGateHost" . }} at the Gateway as well — the wildcard record covers it.

The preview gate is off (previewGate.enabled=false): projects that keep

keep spec.previews.protected get no preview URL at all.

{{ if eq (include "kitchen.collectorEnabled" .) "true" -}}
A telemetry agent runs on every node: container logs into `otel_logs`, the
kubelet's and the node's metrics into `otel_metrics_*`, and whatever
applications export over OTLP into those and `otel_traces`. The operator
creates every table and keeps it at {{ .Values.kitchen.observability.clickhouse.retentionDays }} days of retention:

  kubectl -n {{ .Release.Namespace }} rollout status ds/{{ include "kitchen.collectorFullname" . }}
  kubectl get kitchen default -o jsonpath='{.status.conditions[?(@.type=="TelemetrySchemaReady")].message}'

Then ask for a project's logs, or a build's:

  SELECT Timestamp, Body FROM otel_logs WHERE project = '<project>' ORDER BY Timestamp DESC LIMIT 100
  SELECT Timestamp, Body FROM otel_logs WHERE build = '<build>' ORDER BY Timestamp
{{- else if .Values.collector.enabled }}
No telemetry agent was installed: there is no telemetry store to ship to.
{{- else }}
The telemetry agent is disabled (collector.enabled=false). Nothing collects
logs or metrics, and applications have nowhere to export OTLP to.
{{- end }}

Cluster prerequisites Kitchen assumes: Cilium as the CNI with
gatewayAPI.enabled=true, the Gateway API CRDs, and a reachable address for the
Gateway (L2 announcements/BGP, or cloudflared).
